# hugo-ckan: a static CKAN front end

This project renders a CKAN open-data portal as a static website with Hugo.
`harvest.py` takes a snapshot of any CKAN instance's metadata through the
public Action API, and Hugo turns that snapshot into the full browsing UI
plus read-only JSON endpoints. Nothing runs on a server at request time:
no Python, no PostgreSQL, no Solr.

```sh
make harvest CKAN_URL=https://demo.ckan.org LANG=en   # writes data/ckan/*.json
make serve                                            # http://localhost:1313
make build                                            # writes public/
```

Requirements: Hugo ≥ 0.126 (extended), which adds content adapters, and Python 3.
The harvested snapshot (`data/ckan/`) is not committed. Run `make harvest`
before building locally.

## Publish your own portal mirror (template)

1. Click **Use this template → Create a new repository**.
2. In the new repository, go to **Settings → Pages** and set **Source** to
   **GitHub Actions**.
3. Go to **Settings → Secrets and variables → Actions → Variables** and add:
   - `CKAN_URL` (required), e.g. `https://demo.ckan.org`
   - `CKAN_LANG` (optional, default `en`): the language to use on multilingual portals
   - `CKAN_MAX` (optional, default `0` = all): a cap on datasets, handy for trial runs
4. Run **Actions → Harvest and deploy → Run workflow**, or push to `main`.

The workflow (`.github/workflows/deploy.yml`) harvests the portal, builds the
site with the correct Pages base URL, and deploys it. After that it
re-harvests daily; change the `cron` line to adjust how often. The workflow
does nothing until `CKAN_URL` is set, so a fresh copy never shows failing
runs. GitHub pauses scheduled workflows in repositories with no activity for
60 days; re-enable them from the Actions tab.

## How CKAN features map to static files

| CKAN | Here |
|---|---|
| `/dataset/<name>` | One page per package, generated by a content adapter (`content/dataset/_content.gotmpl`) |
| `/dataset/<name>/resource/<id>` | One page per resource, at the same URL as in CKAN |
| `/organization/<name>`, `/group/<name>` | Hugo taxonomies, with term metadata from the adapters, so the URLs match CKAN's |
| Solr search and facets on `/dataset/?q=&tags=&res_format=…` | Browser-side search over `/index.json`. It accepts **CKAN's own query parameters**, so existing links keep working. Without JS, the page shows a paginated list and links facets to pre-rendered tag, format and license pages. |
| Resource views (recline, geo) | `assets/js/preview.js` reads from the source portal's DataStore API when it exists, otherwise it fetches the file directly and renders CSV/JSON/GeoJSON/images |
| `package_show`, `resource_show` | `…/<page>/index.json`, wrapped like the Action API response |
| `package_list`, `organization_list`, `group_list`, `tag_list`, `license_list`, `status_show`, `current_package_list_with_resources` | Static files under `/api/3/action/` (with and without `.json`) |
| ckanext-dcat | `/catalog.jsonld` (DCAT JSON-LD) |

`?id=` style API calls can't be answered by plain static hosting. See
`nginx.conf.example` for a three-line rewrite, or use equivalent redirect
rules on Netlify or Cloudflare.

## What you give up

- **Writes.** There is no login, dataset editing, uploads, or harvesting
  into the site. Edit in a real (possibly private) CKAN, or edit the JSON in
  git, then rebuild. Running a rebuild on a schedule or webhook works well.
- **Freshness.** The site is exactly as current as the last harvest.
- **Search scale.** The browser-side index is about 670 bytes per dataset
  (1.7 MB raw, 170 KB gzipped for 2,605 datasets). Past roughly 20–30k
  datasets, switch to Pagefind or a sharded index.
- **DataStore SQL and filtering, activity streams, following, private
  datasets.** Previews still call the source portal's DataStore while it
  stays online.
- **Resource files are linked, not mirrored.** Copying them into `static/`
  would make the site fully self-contained.

## Measured (dati.comune.milano.it: 2,605 datasets, 5,969 resources)

Hugo 0.128 on this machine: 17,431 pages and 1,322 paginator pages built in
about 10 s. About 180 MB of output, half of it per-resource HTML and JSON.
